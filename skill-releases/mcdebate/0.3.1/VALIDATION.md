# mcdebate 0.3.1 验证记录

日期：2026-10-18。状态：**供 review；手机端和真实交易未验收**。0.3.0 的源文件与安装包保持不变，本版另存为 0.3.1。

## 改动依据与内容

本轮针对 [0.3.0 DeepSeek 回归记录](../../../evals/mcdebate/RESULTS-2026-10-18.md)里的报价过期、候选刷新、UNKNOWN 查单、旧链接续接、注册未知后错误建议，以及冻结结账后的错误下一步。

- 结账状态 QUOTED 报价过期时，付款人可见官方核价工具就立即只读核价；成功后**先上报新 QUOTED，再请用户确认新金额**。记录报价不等于建单，旧确认不授权按新价提交。
- 用户索要已有支付链接或 UNKNOWN 的结果时，先刷新房间；UNKNOWN 随后用同一账户查已有订单，无需重复问是否允许只读查单。
- 本人 report_item 刷新候选后，即使旧 ready 仍为 true，也重新 set_ready 更新快照；轮询本身不会更新。
- 注册结果未知且无本人凭证时，不承诺能靠房间号/观战链接恢复房主身份，不把重复注册当核对；缺原 watch_url 时不输出猜测链接，绝不能把 player_token 放进观战链接。
- 固定结账后清单与新局冻结；“只看价格”不等于允许直接改单。辩论及其用户说明均避免没有资料支持的营养、原料、销量断言。

评估器只把模型请求发到 DeepSeek `deepseek-flash`；房间与麦当劳工具定义来自本地或合成场景，业务调用不会出网。模型自行选工具；评估器没有强制下一步、补玩家身份或在提前停止后发送“继续”提示。`quote-expired-storelike` 也是合成数据，只是用了更像实际门店的名称与编码，绝非真实订单测试。22个共同场景的答复与工具轨迹可在本地 [对照页面](../../../.local/skill-evals/mcdebate-0.3.1-review.html) 查看；`without_skill` 指旧版0.3.0。

**自动断言通过不等于整段答复准确。** 单次结果不能证明手机端的 Skill 加载、工具发现、后台运行或双 Agent 实时协作稳定；合成等待不等于真实5秒网络轮询。最终完整回归之后补了注册未知与冻结清单的文字，并只重跑了受影响场景；没有宣称最后快照再次全量23场景通过。

## 尚未解决

1. **过期报价推进仍不稳定。** 最终完整回归的示例门店、相似门店两场景都识别旧价不能建单，却停在询问能否重新核价。前面的重复试验中有成功走完的轨迹，也有核价后等待用户确认才想上报 QUOTED 的轨迹。仅靠提示词尚不能保证这条只读流程每次自主完成。
2. **观战链接仍需防模型漏字。** 最终回归中复制正确；此前同版开发过程曾漏掉重复 token 的末段，也曾在无原链接时拼出包含本人 player_token 的错误观战 URL。补写了缺原值禁止输出和裁判答复不附猜测链接的规则，但提示词不能成为确定性保密/复制机制。未来需要服务端提供更短的只读分享凭证或由客户端直接渲染原 `watch_url`。
3. **自然语言还有误导风险。** 最后“只看价格”重复场景没有建单，但个别答复仍把已上报报价讲成“没核价”，或提议先选取餐方式；注册未知有时仍建议刷新连接器、之后新开房间。服务端版本/锁定检查仍负责阻止非法修改与重复提交。
4. **缺少手机端验证。** 豆包 Work 与 WorkBuddy 的引用文件读取、连续等待、跨客户端接力和真实官方 MCP 工具显示，需要在新会话安装本版后检查。

本版不作为生产验收通过的标记。若要继续提高报价过期与链接的确定性，下一步应把关键约束放进工具返回/服务端动作或客户端渲染路径，而不只追加 Skill 文本。

## 手机 review 建议

分别导入 packages 中对应 ZIP，在两个客户端新会话启用本版和已有的两个 MCP。A 说“mcdebate 开始”，核对完整观战链接；B 用房间号加入，不另说偏好，检查是否沿用 B 立场并持续等待。结账演练可以停在核价与用户确认之前，不需要创建真实订单。记录客户端、原话、工具可见性和停止位置，避免把客户端中断误判为服务端离线。
