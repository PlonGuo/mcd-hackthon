# mcdebate 0.3.5 验证记录

日期：2026-10-20。状态：**本地 review 版，尚未部署；新版豆包 Work / WorkBuddy 手机端未验收。**

## 本版行为

- 用户已要求开始或加入对战、本人所需信息齐全后，自动完成候选查询上报、准备与等待；不再以“准备好了吗”“对方在线了吗”作为开局确认。
- 房主等待另一位加入；B 等待房主锁店与建立首局。已有共享立场直接复用；缺本人真实选择才问。
- 等待调用 `get_room_state(since=0,wait_ms=5000)`，不传 `battle_id`。短暂离线或尚未准备保留当前局，条件恢复后房主自动开局。
- 用户说“先别准备”时先刷新，仍处于筹备且本人已准备则撤回本人准备；只说“停止等待”不推定撤回。门店确认和购买确认仍由用户作出。
- 等待实际超过5分钟、宿主明确中断、用户叫停或不可恢复错误时如实停止。5秒为服务端等待参数，实际间隔包含网络与模型耗时；Skill 无法唤醒已结束的另一端会话。

## 最终验证

模型为 `deepseek-flash`。仅模型请求经过网络；房间和官方麦当劳业务回执为本地模拟，**真实业务调用为零**。

| 项目 | 结果 |
| --- | --- |
| 房主等加入 → 建局 → 准备 → 开局 | 3/3 |
| 开局遇短暂离线 → 轮询 → 恢复后重试 | 3/3 |
| B 加入后等房主锁店，连续轮询 | 3/3 |
| 用户明确先别准备，撤回本人 ready | 3/3 |
| 门店未选时展示候选，不替用户锁店/准备 | 3/3 |
| 既有关键行为：B 立场、离线等待、裁判等待、候选刷新后重新准备、付款人交接、未授权不下单、删除本人行、拒绝删除他人行 | 8/8，各一次 |

最终筹备专项目录为 `.local/skill-evals/035-review-preparation`，既有回归为 `035-regression`。自动检查覆盖工具参数、次数、顺序、角色凭证和禁止操作。新筹备场景用实际 `buildAgentView` 生成工具回执中的下一步指引；旧会话快照保留，以检查恢复时刷新。未到齐等不允许的筹备操作会在评估中直接失败，不用预设成功回执掩盖。

配套代码检查：128 项测试通过；类型检查、Node 构建与 Workers dry-run 通过。观战页桌面/手机浏览器检查覆盖自动跟随、读历史不跳动、新消息提醒、评分状态、评分折叠、清单导航、跨局更新、只读结账、XSS 文本显示、粒子生命周期与打包后运行。Skill 格式、归档正文、两端 ZIP 和 SHA256 校验通过。

## 失败记录与评估修正

- 旧 0.3.4 在本次新增的“等加入、开局离线”各5次基线中为 **4/10**：提前结束等待，以及把开局参数中的 battle_id 复制到读取工具。
- 仅补充 Skill 的初稿为 **6/15**；接入当前服务端指引后的一轮为 **10/15**；后续修订一轮为 **9/15**。出现过跳过刷新、提前建局、只说继续轮询却结束执行，以及用户说先别准备后仍重复询问。
- “只看候选门店”最初强制先刷新房间，过度约束了只展示历史候选的安全答案；改为检查不擅自锁店、不准备、不下单，允许一次刷新。又为合法的只读重新搜索补上模拟回执。最终通过率与早期轮次不构成严格同条件对比。
- 没有通过注入“继续调用”消息强制模型重试，未忽略失败样本。上述早期轮次均保留在本地记录中。

## 验证边界

- **不能保证手机后台持续执行。** 两个客户端仍应各自保持会话执行；宿主挂起、工具次数限制或模型结束回复后可能需要用户恢复。真正无人工唤醒的后台托管需要独立的执行机制，不是增加 Skill 文案就能保证。
- 本次15项只检验筹备动作，不是完整 Skill 全流程通过率；最终未重跑全部历史场景。人工检查还发现 B 的3次入房测试中有2次直接继续工具调用，未在中途立即向用户展示房间号和观战链接；该交付时机尚不稳定，不能宣称所有入口行为已完全通过。
- 当前发布包含本地服务端指引修正。只导入0.3.5、仍连接旧服务端时，不应期待与最终专项相同的结果。
- 未在本轮操作真实门店、建单、付款、取消官方订单或退款；支付与身份边界未放宽。有限次数模型通过不代表真实客户端必然遵循。
