# mcdebate 0.3.0 验证记录

日期：2026-10-18。状态：**供 review 的版本；尚未通过豆包 Work / WorkBuddy 手机验收**。本次没有修改或部署 MCP 服务，没有创建真实订单或付款。

## 本次修改

- 将开始、加入、续接的第一个动作写成表格；保留返回观战链接原样复制与本人身份约束。
- 区分自己推进、等待另一位 Agent、等待用户；持续调用 `get_room_state(wait_ms=5000)`，解释通用 `await_user` 和宿主中断边界。
- 明确 B 沿用共享的 B 立场，本局准备读取 `battle.ready`；本人重新上报候选后重新准备，避免候选快照过期。
- 结账按房主/付款人分工：复用已有提名、等待接受、固定方案、领取及核价；房主也可兼任付款人。
- 明确 QUOTED / SUBMITTING 成功后分别取得新版本；空订单列表不证明未建单，UNKNOWN 不允许据此解除或重下。
- 保留 AGENT_REPORTED 真实路径与 TEST_FIXTURE 模拟路径的区别，缺官方工具时说明缺失能力；价格、规格根据官方资料发言。

评估采用本地 MCP 工具定义和合成业务返回；模型自行选工具，脚本不补身份、不强制下一步、不在提前停止后发送纠错提示。只有模型请求访问网络；全部房间、官方查询、建单和支付工具均为本地模拟。

**21/22 是自动断言覆盖范围内的一次观测，不是实际业务成功率。** 断言检查链接、参数、次数和顺序，不能完整判断自然语言含义。部分场景在指定动作处结束，只验证局部流程；没有完成整场双手机对局。耗时不包括真实5秒等待或客户端加载。

开发期间保存了多轮失败与重复试验，曾发现链接丢字符、重复提名、空列表被误判为未下单等波动。中途修过场景返回形状、补过合法工具分支，也改过 Skill，不能将这些不同快照的结果混算成最终成功率。最终对比使用同一组22场景与相同模型配置；本次没有完成“最终快照全量每版本各3次”，不宣称达到该稳定性门槛。

## 仍需改进与人工发现

1. **过期报价仍可能多问一次。** 本轮识别过期并未建单，但停在“是否重新核价”。合成的 `EVAL_STORE` / 示例餐厅名称也影响了判断。Skill 已写直接只读核价，尚未证明模型稳定遵守。
2. **已有链接可能跳过刷新。** 本轮复制了正确原链接且未重复建单，但没有按正文先读取当前状态；不能凭历史答复保证链接仍有效或订单仍待支付。
3. **注册未知的后续建议不稳。** 没有立即重复调用，但答复仍建议用户确认后重试或检查服务恢复；服务恢复不等于找回原身份。本轮不把“只调用一次”算作完整异常处理通过。
4. **冻结状态的下一步描述不严谨。** 只看价格场景没有建单，却建议直接改清单/再开局，省略了先按规则取消结账的前提。后端仍负责拦截不合法操作。
5. **输出还偏技术化。** 出现原始时间戳、内部状态和“AGENT_REPORTED＝真人上报”等不准确解释；UNKNOWN 答复中的“可能重复扣款”也不够准确，应说重复建单，支付仍由用户完成。

以上问题没有被自动断言全部覆盖，因此本版适合 review 和继续手机验证，不能标为全部验收完成。安全边界继续依赖服务端校验与用户具体确认；提示词无法保证每次执行一致。

## 手机 review 操作

1. 分别导入本目录 packages 中的豆包 / WorkBuddy ZIP，只启用新版 mcdebate，保留已配置的两个 MCP 连接器，开新会话。
2. A 选择技能后说“开始，我选麦乐鸡，对手选薯条”；按提示确认门店。把返回的房间号交给 B，核对两端观战链接一致且能打开。
3. B 选择技能后说“加入这个房间：<房间号>”。先不额外告诉 B 偏好，观察它是否沿用薯条立场，并持续等待到自己的回合。
4. 如需测试结账交接，A 说“准备结账，由B付款”；B 明确同意承担付款角色。验证双方能接续到固定方案、领取及核价即可，**在创建订单前停止**。
5. 记录在哪个客户端、哪一步需要额外说“继续”，以及完整脱敏错误。宿主结束/后台中断时，在对应客户端选择技能说“继续”，不要求另一端自动唤醒。
